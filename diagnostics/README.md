# Численные проверки

## Текущие инструменты

Штатный профиль задаётся единственным файлом [solver_profile.json](../solver_profile.json). Решатель читает его через `solver_settings.py`; сводка штатного запуска получает фактические настройки из экземпляра решателя. `tuned_corrector_profile.json` — ссылка на этот файл, а не копия параметров. Текущий `tuned_cases_plan.json` тоже ссылается на него. В исторических планах параметры сохранены явно как снимки соответствующих экспериментов.

λ — угол в оборотах, κ — отношение радиусов. Обвязка создаёт нормированную геометрию проекта и фиксирует время `2π T_a(λ,κ)`. Она не меняет формулы управления и правила инициализации решателя.

| Инструмент | Назначение |
|---|---|
| `tune_hyperparameters.py` | Испытания профилей, бюджет вычислений, проверка всех принятых решений |
| `stability_sweep.py` | Простые серии устойчивости, необязательный контроль времени процесса |
| `common.py` | Общий запуск процессов, атомарная запись результатов, сохранение NPZ и независимое интегрирование |
| `summarize_tuning.py` | Таблица испытаний, сводки отдельно по сериям, попарное сравнение одинаковых задач |
| `summarize_stability.py` | Таблица серий устойчивости, включая исторические |
| `trace_base_start.py` | Подробная трасса коррекции базового примера |
| `analyze_base_full.py` | Проверка базовой трассы; необязательное сравнение с явно переданной другой трассой |
| `probe_jacobian_steps.py` | Сравнение разностных Якобианов на явно выбранной сохранённой точке базового примера |
| `validate_quadratic_initial.py` | Независимая проверка начального квадратичного решения |

Все команды выполняются из корня проекта в окружении основного README. Выходной каталог запуска должен быть новым.

```powershell
python -X utf8 -B diagnostics/tune_hyperparameters.py --plan diagnostics/tuned_cases_plan.json --output outputs/my-tuned-run --jobs 3
python -X utf8 -B diagnostics/summarize_tuning.py outputs/my-tuned-run --output outputs/my-tuned-report
```

Чтобы заменить профиль в произвольном плане, передайте `--profile solver_profile.json`. Разрешается и JSON-ссылка `{"profile_file": "../solver_profile.json"}`; путь считается от файла ссылки или плана. Перед запуском ссылки раскрываются, и фактический профиль записывается в копию плана. Настройки предварительного квадратичного уточнения остаются исходными; профили эксперимента применяются к последующим ограниченным коррекциям. Прежний базовый шаг разностей для контрольных профилей задан явно, а не зависит от текущего штатного значения.

Каждый случай работает в отдельном процессе; потоки BLAS ограничены единицей. Времена параллельных прогонов не являются изолированным бенчмарком. Число фактических вычислений включает дополнительные обращения для Якобиана. `elapsed_seconds` нового рабочего процесса включает его независимые проверки; в ранних результатах подбора проверка всех точек выполнялась после этого замера.

## Результат и ошибки

`result.json` внутри каталога случая — основной источник статуса. Общая `results.json` собирается из этих же записей. Оба вида серий используют один протокол:

- Пока идёт расчёт или проверка, `status=running`. `stage` различает `starting`, `solve`, `verification`, `done`.
- `solve_status` отдельно хранит результат продолжения. `completed` становится итоговым статусом только после успешной независимой проверки; нарушение допуска даёт `verification_failed`.
- `verification_status` различает `not_run`, `passed`, `failed`, `error`, `interrupted`. Исключение при проверке сохраняется как ошибка с этапом `verification`.
- Аварийный выход процесса переписывает запись как `process_error`, даже если до аварии в ней был успешный статус. Выход без финальной записи тоже считается ошибкой процесса.
- `evaluation_budget` и `timeout` — ограничения бюджета, а не доказательства несходимости. Оконченные промежуточные решения сохраняются; `last_accepted` может быть `null`, если первого решения ещё нет.

`progress.json` содержит последнюю попытку; её α не следует выдавать за достигнутое. Последняя принятая точка хранится в `last_accepted.json` и `last_accepted.npz`. Общие принятые решения сохраняются в `solutions.npz` до независимой проверки, поэтому ошибка проверки их не уничтожает.

Сводщик не засчитывает `completed` без подтверждённой проверки. Он допускает отсутствующие счётчики и пустой `last_accepted` при аварии. Общие суммы разделены по сериям и профилям. Попарная таблица сопоставляет одинаковые λ,κ, допуски, фазу и границы α, условия округления и способ старта; повторы учитываются медианой. Задачи с незавершённым запуском вынесены в число исключённых, а не сравниваются как полные проходы.

Независимая проверка использует DOP853, без повторной оптимизации. Для подбора проверяются все принятые решения с rtol=1e-11, atol=1e-13, max_step=T/200; для обычной серии — последнее решение с rtol=1e-10, atol=1e-12. Функционалы Q,L оцениваются трапециями по адаптивной сетке; число активных дуг и развёрнутый угол являются диагностическими показателями.

## Явные входные данные для анализа

```powershell
python -X utf8 -B diagnostics/trace_base_start.py actual outputs/my-base-trace
python -X utf8 -B diagnostics/analyze_base_full.py outputs/my-base-trace
python -X utf8 -B diagnostics/analyze_base_full.py outputs/my-base-trace --reference outputs/another-base-trace
python -X utf8 -B diagnostics/probe_jacobian_steps.py outputs/my-base-trace/accepted.npz outputs/my-jacobian.json --alpha 0.6
```

Анализатор и проверка Якобиана работают с базовой геометрией λ=0,5,κ=1,5. Они не ищут конкретные локальные папки прошлых опытов. `legacy` у трассировщика означает только прежние сопряжённые переменные: на текущей версии решателя это не воспроизводит старую ограниченную инициализацию при α=0. Для точного исторического повторения нужны указанные в отчёте версия исходников и сохранённые входные данные.

## Исторические эксперименты и сохранённые выводы

При исправлении пунктов ревью 8–11 правила начальной инициализации из пункта 7 сохранены по указанию пользователя. Контрольный штатный проход достиг α=1 за 20,10 с; все 11 массивов траекторий точно совпали с предыдущим запуском. Независимая максимальная невязка — 7,7201e-8. Прошли 36 тестов, включая аварии процесса и проверки, преждевременный успешный статус, пустой бюджет, загрузку пользовательских настроек и сопоставление одинаковых задач. Дополнительно проверены реальные короткие прогоны с текущим и историческим профилями, ссылки на профиль, трассировщик и анализ сохранённых данных. Результаты контроля находятся в `outputs/review-8-11-*` и не меняют исторические измерения.

Отчёты и снимки планов сохранены на прежних путях. Они описывают соответствующие версии кода; их числа не обещаны при повторении старого плана текущим решателем. Сырые траектории в `outputs/` не входят в Git. Если историческая проверка использует `seed_from`, нужен явно указанный файл; для повторения из чистого клона сначала создайте соответствующий исходный проход.

- [D1_D3_FIX_VALIDATION_2026-10-22.md](D1_D3_FIX_VALIDATION_2026-10-22.md): повторные планы `d1_d3_*`, исправление старта и локального шага.
- [BASE_START_APPLICATION_AUDIT_2026-10-22.md](BASE_START_APPLICATION_AUDIT_2026-10-22.md): проверка применения аппроксимаций и старого старта.
- [QUADRATIC_INITIAL_CAP_2026-10-22.md](QUADRATIC_INITIAL_CAP_2026-10-22.md): выбор начального A по неограниченной траектории.
